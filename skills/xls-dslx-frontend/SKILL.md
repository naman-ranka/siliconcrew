# The DSLX frontend

DSLX is a functional hardware description language; the XLS toolchain compiles
it to Verilog through an IR, with optimization and scheduling in between. It
earns its place on a narrow class of designs and gets in the way everywhere
else.

## When it is the right tool

Pure datapath, where the hard part is the arithmetic and not the control:
fixed-point math, CRCs and checksums, encoders and decoders, bit manipulation,
filters, small transforms. Two things make it worth the detour — the language's
own `#[test]` functions verify the algorithm before any Verilog exists, and the
compiler's area and delay estimate lets you compare two formulations without
paying for a synthesis run.

## When it is the wrong tool

Anything whose difficulty is interface or control: bus protocols, handshakes,
arbiters, state machines with externally-visible timing, memory interfaces.
Expressing those in DSLX fights the language and produces Verilog you cannot
review. Write them directly in Verilog.

## Treat the generated Verilog as compiler output

Never hand-edit it. It is regenerated by the next compile and your edit
disappears — silently, because the file still exists and still compiles. If the
generated module's interface is not the interface you need, write a small
adapter module in Verilog that wraps it: the adapter is yours to edit, the
generated file is not.

Give the adapter the port names and reset behaviour the rest of the design
expects, and record which file is generated and which is hand-written in the
manifest, so a later reader (or a later you) does not edit the wrong one.

## Verify it like any other RTL

A passing DSLX `#[test]` proves the algorithm, not the hardware. Run the
generated module through the normal lint and simulation flow with a testbench
you derived from the spec — the same standard as hand-written RTL, and for the
same reason: the test and the implementation now share an author again.

Debug in the language, not in the output. If the generated Verilog is wrong,
the DSLX is wrong; stopping the flow after the interpreter or after IR
optimization localises which stage introduced the problem far faster than
reading the emitted module.
